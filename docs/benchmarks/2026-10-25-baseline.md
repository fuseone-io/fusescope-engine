## Ingest stages (in process, 5000 requests, 60 000 spans)

Command: `fs-bench stages --requests 5000 [--wal-dir /mnt/fs-bench/fusescope-bench/wal]`

| stage | total | ns/span | note |
|---|---:|---:|---|
| protobuf encode | 55 ms | 913 | |
| wal append + fsync, per request, disk A (LUKS) | 3.44 s | 57 252 | 0.69 ms per fsync |
| wal append + fsync, per request, disk B (plain) | 2.00 s | 33 368 | 0.40 ms per fsync |
| otlp → arrow | 388 ms | 6 459 | 155 k spans/s on one core |
| concat + sort | 155 ms | 2 577 | |
| parquet encode | 180 ms | 2 992 | 60 000 spans → 3 MiB |
| upload (local store) | 1 ms | 22 | not representative; S3 measured by `load` |
| hot-window filter + project | 105 ms | 1 745 | |

`--sync always` measures the same as per request because the ingester already
syncs once per request.

Memory: the converted corpus is 92 MiB of Arrow for 20 MiB of protobuf and
3 MiB of Parquet. Before the fix in the same change set, it was 1 840 MiB: the
per-request builders kept their allocation capacity, 30 KB per span, which
would have tripped the byte-based flush threshold after a few thousand spans.
Compacting the batch at the end of conversion removed it and also halved the
conversion time (805 ms → 388 ms) by allocating less.

**Reading.** The WAL fsync is the only stage above 10 µs per span and is 5 to
9 times the next one. With one fsync per request and the WAL under a mutex, an
ingester cannot acknowledge more than roughly 1 400 (LUKS) to 2 500 (plain)
requests per second whatever the CPU does. Group commit is the next change.

## Load (release server, all roles, WAL on disk B, bucket RustFS)

Command: `fs-bench load --endpoint 127.0.0.1:4317 --duration-secs 30 --concurrency C`

| senders | req/s | spans/s | p50 | p95 | p99 | errors |
|---:|---:|---:|---:|---:|---:|---:|
| 8 | 2 196 | 26 354 | 3.20 ms | 5.23 ms | 6.95 ms | 0 |
| 32 | 2 216 | 26 589 | 13.40 ms | 24.73 ms | 49.62 ms | 0 |

Throughput is flat between 8 and 32 senders and latency grows linearly with
concurrency: the pipeline is serialised on the WAL fsync, as the stage numbers
predict (0.40 ms per fsync → about 2 500 requests per second ceiling; the
measured 2 200 includes the gate and conversion under the same lock). 20 L0
files were flushed in the two runs; no rate limit, capacity or flush failure.

Against the DESIGN.md target of 150 MB/s of uncompressed OTLP per ingester:
2 200 requests × 4 KiB ≈ 9 MB/s. Group commit should lift the ceiling to the
conversion cost, about 150 k spans/s per core; the rest is parallelising
conversion across cores.

## Query suite (release server, 20 L0 files from the load runs, hot window on)

Command: `fs-bench query --endpoint 127.0.0.1:8815 --iterations 10`

| query | rows | p50 | p95 | max |
|---|---:|---:|---:|---:|
| trace by id | 12 | 150 ms | 154 ms | 154 ms |
| span list, 1 service, 15 min, promoted attribute | 0 | 126 ms | 126 ms | 126 ms |
| p99 latency per service, 24 h | 20 | 129 ms | 325 ms | 325 ms |
| dashboard: rate and errors per service, last 5 min | 0 | 125 ms | 126 ms | 126 ms |
| top operations by p95, 1 h | 20 | 133 ms | 137 ms | 137 ms |

The two zero-row queries ran more than 15 minutes after the load, so their
windows were empty; they still cost 125 ms. That is the floor of a statement
today, independent of data: `GetFlightInfo` plans the statement (token lookup,
tenant lookup, catalog cache, hot-window fan-out with a fresh connection per
ingester) and `DoGet` plans it all again. The metrics confirm it: 102
statements planned for 51 queries, 51 fan-outs. Removing the second planning
and reusing connections to ingesters is worth about 100 ms on every query
before any work on files.

**Reading.** Above the floor, trace lookup opens every candidate file because
pruning only understands time and service; with 20 files that is 25 ms, with
thousands of L0 files it will not be. The `trace_id → files` index (fs-index)
is what the 300 ms target depends on at scale, and L0 → L1 compaction is what
keeps the candidate list short. Both are on the agreed list after group
commit and the planning fix.

A first run of this suite failed on every query with a GROUP BY or ORDER BY on
a dictionary column: Flight hydrates dictionaries in transit, and the union of
hot rows with files saw `Utf8` where the schema said `Dictionary`. The
end-to-end test only counted rows, so it never grouped. Fixed in the same
change set, with the test extended to group and sort over hot and file rows.
